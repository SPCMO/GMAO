GMAO — Matériel hydrométrique

Documentation d'utilisation, d'architecture et de suivi des évolutions

Utilisation

Lancer l'application locale

L'appli sert à consulter/modifier la base (dashboard, formulaires). Elle utilise un environnement Python dédié (venv) où Flask est installé — ne pas la lancer avec le Python système (ça produit une erreur ModuleNotFoundError: No module named 'flask', typique si on utilise le bouton "Run" d'un IDE comme Thonny au lieu du venv du projet).

"GMAO\venv\Scripts\python.exe" "GMAO\run.py"

Puis ouvrir http://localhost:5000 dans un navigateur. Cette page d'aide est aussi accessible directement depuis l'appli via le lien 📖 Aide en haut de chaque page.

Vue globale (dashboard)

Page d'accueil en deux parties : une carte à gauche (un marqueur par site géolocalisé — pas par équipement — coloré selon l'UH de gestion ou le statut du site, avec au clic le nom du site et la liste cliquable des équipements qui y sont actuellement affectés) et le tableau à droite. Le menu déroulant filtre par site, le champ de recherche filtre par nom d'équipement. Déplacer ou zoomer la carte filtre également le tableau sur la zone visible (les équipements sans coordonnées restent toujours affichés, puisqu'ils n'ont pas de position à comparer) — un bandeau « Le tableau est filtré sur la zone visible de la carte » apparaît, avec un lien pour réinitialiser.

Une pastille grisée avec une icône 🔧 signale un site de maintenance, une pastille gris foncé un site sans aucun équipement affecté, une pastille blanche à croix rouge semi-transparente un site fermé. Une case « Masquer les sites fermés sur la carte » au-dessus de la carte permet de les cacher temporairement sans les faire disparaître de la liste des sites — seule leur suppression complète depuis le Gestionnaire des sites les retire définitivement de la carte.

La carte affiche une échelle dynamique en bas à gauche, et un sélecteur en haut à droite permet de basculer entre le fond Plan (OpenStreetMap) et Satellite (imagerie Esri) — toujours déplié (et réduit en taille) pour qu'il reste visible sans avoir à deviner qu'il est cliquable ; disponible aussi sur les mini-cartes de pointage d'un nouveau site. Une légende repliable (bouton 🗺️ Légende) en bas à droite de la carte rappelle la signification de chaque couleur/icône.

Dans le tableau, la colonne Tps restant (j) indique le nombre de jours restants avant la date de péremption calculée (durée de vie + date de 1ère mise en service), en rouge si déjà dépassée — triable comme les autres colonnes, y compris quand le rappel n'est pas configuré.

Le tri par défaut de cette liste (retirés en bas, puis par UH/type/sous-type/nom) est configurable dans ⚙️ Paramètres → onglet 🔀 Tri par défaut. Chaque en-tête de colonne reste triable manuellement à tout moment via ses boutons ▲▼.

Ajouter un équipement

Bouton + Nouvel équipement en haut de page : nom, site d'affectation (menu déroulant listant les sites déjà utilisés, avec une option + Nouveau site... pour en créer un directement depuis le formulaire), date d'installation. Un identifiant technique unique est généré automatiquement (utilisé plus tard dans l'URL du QR code).

La date saisie dans ce formulaire est la date d'installation du matériel (qui peut être dans le passé). La date d'affectation au site choisi est toujours celle du jour de la création dans l'outil — les deux dates sont indépendantes.

Localisation et UH de gestion : réglées par site, pas par équipement

La localisation et l'UH de gestion appartiennent au site, pas à l'équipement : tous les équipements affectés à un même site partagent automatiquement sa position et son UH — donc les mêmes destinataires d'alerte (voir Paramétrage). Quand un site existe déjà, le sélectionner suffit — tout est repris automatiquement (aucun champ supplémentaire à remplir). Quand on choisit + Nouveau site..., un encart carte et un menu UH apparaissent pour définir le site (clic sur la carte ou saisie manuelle des coordonnées) ; c'est valable aussi bien depuis le formulaire de création d'équipement que depuis Changer l'affectation. Voir la section 🏢 Gestionnaire des sites ci-dessous pour corriger ou compléter ces informations après coup.

🏢 Gestionnaire des sites

Accessible depuis le bouton 🏢 Sites en haut de chaque page : liste tous les sites connus, le nombre d'équipements actuellement affectés à chacun, leur UH de gestion et leur localisation. Bouton + Site pour en créer un directement (sans passer par un équipement) ; lien ✏️ Modifier par ligne pour corriger la case Site de maintenance, l'UH de gestion ou la position (laisser les champs de coordonnées vides efface la localisation).

Triée par défaut par Statut puis Site (sites fermés en bas) ; chaque en-tête de colonne est triable manuellement (▲▼), et le tri par défaut se règle dans ⚙️ Paramètres → 🔀 Tri par défaut.

Changer l'affectation d'un équipement

Depuis la fiche détail d'un équipement → Changer l'affectation : indiquer le nouveau site et la date de transfert. L'ancienne affectation est automatiquement clôturée (date de fin renseignée) et une nouvelle ligne d'historique est créée. L'historique n'est jamais réécrit, seulement complété.

QR code d'un équipement

La fiche détail d'un équipement affiche son QR code dans un encart à droite, avec un bouton 🖨️ Imprimer (n'imprime que l'étiquette, pas le reste de la page) et 📄 Télécharger en PDF — pratique pour ressortir rapidement l'étiquette d'un seul équipement sans passer par le dashboard.

Générer les QR codes d'une sélection

Depuis le dashboard, cochez les équipements voulus, ou utilisez les boutons Tout sélectionner / Tout désélectionner (comme la case en tête de tableau, ils ne touchent que ce qui est actuellement affiché — donc respectent les filtres site/recherche en cours). Cliquez ensuite sur Générer les QR codes de la sélection : la planche ne contiendra que ces équipements et s'ouvre directement dans un nouvel onglet, avec un bouton 🖨️ Imprimer (impression directe) et un lien 📄 Télécharger en PDF. Un message s'affiche si aucun équipement n'est coché.

Publier les fiches et générer les QR codes (tous les équipements)

Après une ou plusieurs modifications, deux scripts régénèrent le contenu à publier :

"GMAO\venv\Scripts\python.exe" "GMAO\scripts\generate_site.py"
"GMAO\venv\Scripts\python.exe" "GMAO\scripts\generate_qrcodes.py"

Le premier régénère les fiches HTML (une par équipement) dans docs/e/. Le second régénère les QR codes individuels et la planche imprimable dans etiquettes/ (fichier planche_etiquettes.html — à ouvrir dans un navigateur et imprimer). Il faut ensuite pousser les changements vers GitHub pour que les fiches en ligne soient à jour (git add -A, git commit, git push).

Étiquettes

Chaque étiquette imprimée porte le QR code et le nom de l'équipement en clair — utile si le réseau mobile est absent ou instable sur le site (cas fréquent pour du matériel isolé), pour au moins identifier visuellement le matériel sans avoir à scanner.

🔧 Gestion des équipements

Bouton 🔧 Équipements en haut de page : liste de gestion (type, site, UH, statut) avec le bouton + Nouvel équipement et un lien ✏️ modifier par ligne — triée par défaut par Statut, Type puis Équipement (retirés en bas), chaque en-tête restant triable manuellement (▲▼) ; le tri par défaut se règle dans ⚙️ Paramètres → 🔀 Tri par défaut. Le formulaire (création ou modification) couvre :

  • Type / Sous-type — menus déroulants en cascade (le choix du type détermine la liste des sous-types proposés) ;
  • Date de création et Date de 1ère mise en service — la seconde doit être postérieure ou égale à la première (contrôle de saisie automatique) ;
  • Durée de vie, Rappel avant échéance et Rallonge post rappel (en années) — utilisés pour calculer la péremption (voir ci-dessous) ;
  • Retrait définitif (uniquement en modification) — une fois une date de retrait renseignée, l'équipement s'affiche grisé et barré dans la liste d'accueil, avec la raison du retrait (menu déroulant : Usure normale / Vol / Détérioration / Vandalisme / Détérioration par crue / saisie libre).

⚠️ Alertes de péremption

Péremption = date de 1ère mise en service + durée de vie. L'alerte se déclenche rappel années avant cette échéance. Un équipement en alerte affiche une icône ⚠️ dans la colonne dédiée du dashboard ; cliquer dessus ouvre sa fiche de modification avec une question « Souhaitez-vous le prolonger ? » :

  • Non — rien ne change, l'alerte reste affichée ;
  • Oui — la durée de vie effective est augmentée de la rallonge configurée (visible dans la colonne Durée de vie prolongée et sur la fiche détail). La péremption est recalculée sur cette nouvelle base, et l'alerte réapparaîtra plus tard si la nouvelle échéance est également dépassée.

Le mail envoyé (voir Paramétrage) précise si la durée de vie affichée est déjà une durée prolongée.

Architecture

Le principe central : le QR code n'encode jamais les données du matériel directement (elles deviendraient fausses au premier changement d'affectation), mais un lien stable vers une fiche consultée en ligne, générée dynamiquement depuis la base.

1. Base SQLite (data/gmao.db) — source de vérité unique : table equipement (nom, date d'installation) et table affectation (site, date de début, date de fin — NULL = affectation en cours). L'historique se déduit naturellement de cette seconde table.
↓ édité via
2. Appli Flask locale (run.py + app/) — dashboard, formulaires de création/changement d'affectation. Usage local uniquement, pas exposée sur Internet.
↓ génère
3. Générateurs statiques (scripts/generate_site.py, scripts/generate_qrcodes.py) — produisent une fiche HTML autonome par équipement (docs/e/<id>.html) et les QR codes correspondants (etiquettes/).
↓ publié via git push
4. GitHub Pages (github.com/SPCMO/GMAO, dossier docs/) — hébergement public gratuit des fiches, accessible depuis un smartphone en scannant le QR code, y compris hors réseau interne.

Usage multi-postes

Chaque poste garde sa propre copie du code (son propre .bat), mais peut pointer vers une base SQLite partagée sur le réseau au lieu de sa base locale, via le menu ⚙️ Paramètres. Tous les postes configurés sur le même chemin réseau voient alors les mêmes équipements et affectations. Le chemin choisi est propre à chaque poste (fichier settings.json, non versionné) — chacun le configure une fois.

SQLite sur un partage réseau tolère bien un usage occasionnel à quelques personnes, mais n'est pas conçu pour des écritures strictement simultanées par de nombreux utilisateurs. Si l'usage se développe fortement, un vrai serveur central (une seule instance de l'appli, accédée par navigateur) serait plus robuste.

Installer l'appli sur un nouveau poste

Le dossier réseau (2026_GMAO) sert de copie du code et de stockage de la base partagée — il ne contient volontairement pas d'environnement Python (venv), et Lancer_GMAO.bat ne peut pas s'exécuter directement dessus (Windows ne supporte pas un dossier réseau \\... comme répertoire de travail). Pour un nouveau poste :

  1. Copier tout le dossier GMAO (depuis le réseau ou GitHub) sur le disque local, par exemple D:\GMAO
  2. Double-cliquer sur Test_pr_install.bat : il détecte les versions Python disponibles, crée l'environnement virtuel (venv) si besoin, vérifie chaque dépendance (Flask, qrcode, Pillow, openpyxl, reportlab) et propose d'installer celles qui manquent
  3. Lancer Lancer_GMAO.bat, puis dans le menu ⚙️ Paramètres, indiquer le chemin réseau de la base partagée (voir ci-dessous)

En cas de souci, la méthode manuelle reste possible : python -m venv venv puis venv\Scripts\python.exe -m pip install -r requirements.txt.

Emplacement de la base (menu Paramètres)

Le menu ⚙️ Paramètres de l'appli permet de changer l'emplacement de la base SQLite sans toucher au code : local (par défaut) ou chemin réseau partagé, par exemple :

\\10.11.208.239\suivi\Suivi_hydrométrie\00_Projets_en_cours\2026_GMAO\data\gmao.db

Ce choix est enregistré dans settings.json à la racine du projet — un fichier propre à chaque poste, exclu du dépôt git (.gitignore), donc jamais publié sur GitHub. C'est ce qui permet de garder un chemin réseau interne hors du dépôt public.

Listes déroulantes et couleurs (menu Paramètres)

La page ⚙️ Paramètres est organisée en 6 onglets pour limiter le défilement : 🗄️ Général (emplacement de la base), 🚨 Alertes mail (SMTP + relais mail + destinataires par UH), 🔧 Équipements (types/sous-types, durée de vie/rappel/rallonge), 🏢 Sites (raisons de fermeture), 🖌️ Couleurs (couleurs de fond) et 🔀 Tri par défaut (voir ci-dessous). L'onglet ouvert est mémorisé le temps de la session : après un ajout/suppression dans une liste, on reste sur le même onglet plutôt que de revenir à « Général ». Chaque liste s'édite par simple ajout/suppression, sans toucher au code.

L'onglet 🔀 Tri par défaut règle, pour l'accueil, le Gestionnaire des sites et le Gestionnaire des équipements, jusqu'à 3 niveaux de tri appliqués au chargement de la page (une colonne non couverte garde son ordre habituel) — l'ordre actuellement configuré est rappelé sous le titre de chaque carte, mis à jour dès l'enregistrement. Ce réglage est partagé (stocké en base, comme les couleurs) — il s'applique donc à tous les utilisateurs de l'outil, pas seulement à ce poste.

Dans l'onglet 🚨 Alertes mail, les trois blocs sont dans l'ordre où ils comptent le plus au quotidien : d'abord les destinataires par UH, puis le relais Apps Script (le canal privilégié sur le réseau SPCMO), puis le SMTP direct en repli si le relais échoue ou n'est pas configuré.

Types et sous-types se réordonnent librement avec les boutons ▲▼ — c'est cet ordre qui s'affiche dans tous les menus déroulants de l'application. Les durées de vie/rappel/rallonge, elles, s'insèrent toujours automatiquement par ordre croissant (pas de tri manuel nécessaire).

Supprimer un type supprime aussi tous ses sous-types. Les équipements qui utilisaient déjà une valeur retirée d'une liste conservent cette valeur affichée (elle disparaît seulement des choix proposés pour les nouvelles saisies).

🖌️ Couleurs de fond (onglet Paramètres)

7 couleurs configurables (UH 11/34/66, site de maintenance, site sans UH configurée, site sans équipement affecté, site fermé), utilisées à la fois pour la légende de la carte du dashboard et pour le fond des lignes de la liste d'accueil (« site sans équipement » ne s'applique qu'à la carte : une ligne équipement a toujours au moins son propre équipement affecté à son site). Chaque couleur a aussi un champ Opacité (%) pour un rendu semi-transparent — utilisé par défaut sur « site fermé » (55 %), à 100 % (opaque) pour les autres.

Priorité en cas de plusieurs statuts vrais à la fois : fermé > maintenance > UH configurée > sans UH.

📧 Alertes de péremption par mail

L'envoi effectif est fait par un script autonome, à lancer une fois par jour :

"GMAO\venv\Scripts\python.exe" "GMAO\scripts\verifier_alertes.py"

Il vérifie tous les équipements, envoie un mail par équipement nouvellement en alerte (destinataires = adresses configurées pour son UH de gestion), puis marque l'alerte comme notifiée pour ne plus la renvoyer les jours suivants — ce marqueur est remis à zéro automatiquement si l'équipement est prolongé, pour permettre une nouvelle alerte à la prochaine échéance.

Déclenchement quotidien à 7h — sur un poste qui reste allumé et a accès au réseau SPCMO (pour la base) et à Internet (pour l'envoi), créer une tâche planifiée Windows :

schtasks /create /tn "GMAO - Verification alertes" /sc daily /st 07:00 /tr "\"D:\charles-eddy.piot\Documents\Perso CEP\Git-Claude IA\GMAO\venv\Scripts\python.exe\" \"D:\charles-eddy.piot\Documents\Perso CEP\Git-Claude IA\GMAO\scripts\verifier_alertes.py\""

Adapter les chemins si le script tourne depuis un autre poste. Vérifier ensuite dans le Planificateur de tâches Windows (recherche "Planificateur de tâches" dans le menu Démarrer) que la tâche apparaît bien, avec un test manuel via clic droit → Exécuter.

Comment le mail part réellement : relais Google Apps Script

Le réseau SPCMO bloque le SMTP direct (587/465, testé et confirmé le 18 août 2026 — timeout avant même l'authentification). Solution retenue : un script Google Apps Script (apps_script/gmao_mail_relay.gs), qui s'exécute côté serveur Google et envoie le mail via GmailApp.sendEmail() — GMAO le contacte simplement par une requête HTTPS (voir « Proxy sortant du réseau RIE » ci-dessous), sans jamais ouvrir de connexion SMTP.

Déploiement (une seule fois) :

  1. Se connecter sur script.google.com avec le compte spcmo113466@gmail.com
  2. Nouveau projet, coller le contenu de apps_script/gmao_mail_relay.gs
  3. Remplacer TOKEN_SECRET par une valeur secrète de ton choix (à retenir, elle sera resaisie dans GMAO)
  4. Déployer → Nouveau déploiement → type Application Web — Exécuter en tant que Moi, accès Tout le monde
  5. Copier l'URL de déploiement (se termine par /exec)
  6. Dans GMAO → ⚙️ Paramètres → section 🔗 Relais mail : coller l'URL et le même jeton secret, Enregistrer, puis ✉️ Envoyer un test pour vérifier

Le SMTP direct reste disponible en repli dans ⚙️ Paramètres (utile si l'appli tourne un jour sur un réseau qui n'a pas cette restriction) : GMAO essaie d'abord le relais Apps Script s'il est configuré, sinon retombe sur le SMTP.

Trois destinations de déploiement

Comme pour les autres outils du service, chaque modification du code est déployée vers trois emplacements :

  1. Dossier local — là où le code est modifié
  2. Réseau SPCMO — \\10.11.208.239\suivi\Suivi_hydrométrie\00_Projets_en_cours\2026_GMAO, copie complète de l'outil (héberge aussi la base partagée pour l'usage multi-postes)
  3. GitHub public — github.com/SPCMO/GMAO, pour l'hébergement des fiches (GitHub Pages)
La base de données du dossier réseau (data/gmao.db) n'est jamais écrasée par ces synchronisations de code — seuls les fichiers du programme sont mis à jour, pour ne pas perdre les données saisies par les utilisateurs.

Publication automatique des fiches

Depuis le 18 août 2026, GMAO régénère et republie automatiquement les fiches statiques (docs/e/*.html) sur GitHub à chaque création, modification ou changement d'affectation d'un équipement, et à chaque création de site — plus besoin de lancer scripts/generate_site.py ni de pousser sur GitHub à la main. Un message apparaît en bas à droite de l'écran (visible sur la page suivante consultée) pour confirmer le résultat :

  • ✅ fond vert — fiches publiées avec succès sur GitHub Pages ;
  • ⚠️ fond orange — les fiches sont à jour et enregistrées localement (rien n'est perdu), mais l'envoi vers GitHub a échoué (voir « Proxy sortant du réseau RIE » ci-dessous : normalement résolu depuis le 18 août 2026, un ⚠️ persistant est à signaler).

Proxy sortant du réseau RIE (git, relais mail)

Constaté le 18 août 2026 : le réseau RIE/SPCMO impose un proxy sortant obligatoire pour toute connexion internet générale — le navigateur l'applique automatiquement (fichier de configuration PAC du poste), mais ni git, ni curl, ni Python (urllib) ne le détectent seuls. Résultat avant correctif : timeout systématique (~21s) sur tout `git push`/appel HTTPS lancé en ligne de commande ou depuis l'appli, alors que la navigation web fonctionnait normalement — ce qui pouvait faussement ressembler à un blocage ciblé de GitHub ou de Google.

Correctif : l'adresse du proxy (pfrie-std.proxy.e2.rie.gouv.fr:8080, trouvée dans le fichier PAC du poste) est configurée en dur dans config.PROXY_RIE, utilisée automatiquement par :

  • app/publication.py — chaque appel git est passé avec -c http.proxy=..., sans dépendre de la configuration git personnelle de qui lance l'appli ;
  • app/mail.py — un ProxyHandler urllib explicite (la détection automatique de urlopen() s'est montrée peu fiable même variable d'environnement définie), avec 3 tentatives en cas de lenteur ponctuelle du proxy.

Fonctionne donc directement sur le poste d'un collègue sans configuration préalable. Une variable d'environnement HTTPS_PROXY, si définie sur un poste, reste prioritaire sur cette valeur en dur (utile si un poste n'est pas sur ce même réseau).

Hébergement GitHub Pages

Dépôt : github.com/SPCMO/GMAO (public). Publication activée sur la branche main, dossier /docs. Le fichier docs/.nojekyll désactive le traitement Jekyll (inutile pour du HTML statique, et source de lenteurs au déploiement sans lui).

Sécurité : le dépôt étant public, son contenu reste techniquement consultable dans son intégralité (pas seulement les fiches individuelles) par quiconque connaît son adresse. Les identifiants d'équipement utilisés dans les URL sont volontairement opaques (non déductibles du nom) pour limiter la découverte, mais ce n'est pas une confidentialité stricte — à reconsidérer si les données venaient à être plus sensibles.

Authentification git

Un token d'accès personnel GitHub (scope Contents uniquement) est enregistré dans la configuration git locale du dépôt pour permettre les git push sans ressaisie. En cas d'expiration ou de révocation, en régénérer un depuis GitHub (Settings → Developer settings → Personal access tokens) et mettre à jour l'URL du remote :

git remote set-url origin "https://<NOUVEAU_TOKEN>@github.com/SPCMO/GMAO.git"

Pour un git push/git fetch manuel depuis un terminal (hors appli GMAO), le proxy RIE doit aussi être configuré une fois côté poste — voir « Proxy sortant du réseau RIE » ci-dessus pour l'adresse, à définir avec :

git config --global http.proxy http://pfrie-std.proxy.e2.rie.gouv.fr:8080
git config --global https.proxy http://pfrie-std.proxy.e2.rie.gouv.fr:8080
